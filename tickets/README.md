# План реализации «Отклика»

## Как пользоваться

Все тикеты выполняются строго по порядку внутри **одного Goal Mode**. Goal создается один раз на весь проект и остается активным до завершения Ticket 014. Тикет — это этап и проверяемый checkpoint внутри общего goal, а не отдельный запуск режима.

Перед первым изменением исполнитель читает этот файл, [готовый промпт Goal Mode](./GOAL_PROMPT.md) и [progress.md](./progress.md). Перед каждым следующим этапом он читает только соответствующий тикет, выполняет его до критерия готовности, фиксирует результат в progress и сразу продолжает следующий тикет без нового запуска Goal Mode.

Каждый тикет заканчивается одинаковым проверяемым состоянием:

1. изменения реализованы и покрыты указанными тестами;
2. весь актуальный проект собирается;
3. `docker compose up --build -d` запускает локальный стенд;
4. health-checks проходят;
5. пользовательский срез тикета можно открыть в браузере;
6. в `progress.md` записаны URL, тестовые данные, команды проверки и известные ограничения.

Следующий тикет не должен ломать демонстрационный сценарий предыдущих тикетов. Общий goal отмечается завершенным только после `DONE` у всех тикетов 001–014 и финального прогона C1–C8.

## Отдельный этап после MVP

Функциональный план 001–014 завершен. Следующая самостоятельная стадия — [Ticket 015: единый UX, навигация и непрерывная история обращения](./015-unified-ux-redesign.md). Для нее подготовлен [отдельный промпт Goal Mode](./UX_GOAL_PROMPT.md): один запуск последовательно выполняет все шесть checkpoints. Перед реализацией Ticket 015 читается полностью и используется как источник истины для публичного интерфейса и всех служебных кабинетов.

## Архитектурная основа

- **Frontend:** TypeScript, React, Vite, mobile-first PWA, Axios, TanStack Query, Zustand, [Material Web](https://www.npmjs.com/package/@material/web).
- **Backend:** ASP.NET Core Web API на актуальном LTS .NET, PostgreSQL, EF Core, Redis, Kafka.
- **Форма приложения:** модульный монолит с отдельным background worker. PostgreSQL — источник истины; Redis — только временные блокировки, rate-limit, presence и короткоживущий cache; Kafka — доменные события и проекции аналитики.
- **Аутентификация сотрудников:** ASP.NET Core Identity и HttpOnly cookie через same-origin reverse proxy. Токены не хранятся в `localStorage`.
- **Анонимный доступ:** криптографический трек-номер; публичные endpoints отделены от staff API.
- **Вложения MVP:** приватный Docker volume за интерфейсом файлового хранилища; метаданные — в PostgreSQL. Публичных URL у файлов нет.
- **Локальный запуск:** Docker Compose. Наличие .NET SDK и Node.js на хосте не требуется; нужен только Docker с Compose.

Планируемая структура:

```text
src/
  frontend/
  backend/
    Otklik.Api/
    Otklik.Application/
    Otklik.Domain/
    Otklik.Infrastructure/
    Otklik.Worker/
tests/
  backend/
  e2e/
docker-compose.yml
README.md
```

## Зафиксированные решения

- Внешних интеграций в MVP нет.
- Оператор не читает чат заявителя с экспертом и не видит внутренние заметки. Для передачи, соисполнителя и пересмотра приоритета используются отдельные структурированные запросы.
- Кризисные контакты конфигурируются. Начальные значения: детский телефон доверия `8-800-2000-122` и короткий номер `124` с мобильного.
- Кризисный флаг выставляет система, приоритет «Срочно» подтверждает оператор.
- Пользовательских сценариев ровно восемь — из раздела 7 ТЗ.
- Формат трек-номера: `ОТК-XXXX-XXXX` с алфавитом без `0/O`, `1/I/l`.
- Лимит вложений: пять файлов, до 10 МБ каждый; PNG, JPEG и PDF.
- Максимум два возврата «Это не помогло».
- Закрытый рабочий цикл не переоткрывается; продолжение той же ситуации создает связанный цикл с общей историей и тем же треком, а отдельная ситуация — новое обращение с новым треком. Реализация запланирована в Ticket 015.
