# Промпт для единого Goal Mode

Скопируйте текст ниже целиком в один новый Goal Mode. Повторно запускать Goal Mode для отдельных тикетов не нужно.

---

Ты работаешь над одной долгоживущей целью: последовательно реализовать весь MVP «Отклик» по тикетам `tickets/001-*.md` — `tickets/014-*.md`, сохраняя после каждого этапа работающий локальный Docker-стенд. Не завершай goal после отдельного тикета. Заверши goal только после `DONE` у всех 14 тикетов и успешной финальной приемки C1–C8.

Если активный goal еще не создан, создай один goal с objective:

> Последовательно выполнить все тикеты 001–014 проекта «Отклик», после каждого checkpoint сохранять доступный локальный Docker-срез и вести progress.md, а завершить goal только после прохождения C1–C8 на финальном стенде.

Не задавай token budget, если пользователь отдельно его не указал.

## Источники истины и порядок чтения

В начале первого хода прочитай полностью:

1. `tickets/GOAL_PROMPT.md`;
2. `tickets/README.md`;
3. `tickets/progress.md`;
4. `Анализ_кейса_Отклик.md`;
5. первый незавершенный ticket-файл.

После этого исполняй только текущий тикет. Следующие ticket-файлы читай по одному непосредственно перед началом соответствующего этапа, чтобы не размывать внимание.

Приоритет при расхождении информации:

1. последние прямые указания пользователя;
2. журнал решений в `tickets/progress.md`;
3. текущий ticket-файл;
4. `tickets/README.md`;
5. `Анализ_кейса_Отклик.md`.

Если пользователь изменил решение, сначала запиши его в журнал решений и отметь затронутые тикеты, затем продолжай работу.

## Непрерывный цикл выполнения

1. Найди в `progress.md` единственный тикет `IN_PROGRESS`. Если его нет, возьми первый `PLANNED` после последнего `DONE` и переведи в `IN_PROGRESS`.
2. Заполни блок «Активный тикет»: номер, objective общего goal, фактическое стартовое состояние, текущий checkpoint, следующий шаг и блокеры.
3. Выполняй checkpoints текущего тикета по порядку. Сначала делай минимальный сквозной tracer bullet от UI до хранения/API, затем ошибки, безопасность и тесты.
4. После каждого checkpoint:
   - сохрани рабочую сборку;
   - запусти актуальный стенд через Docker Compose;
   - проверь health-checks и видимый пользовательский путь;
   - добавь запись в журнал checkpoints с командами, результатами, URL, тестовой ролью/трек-номером и оставшейся работой;
   - сообщи пользователю короткий промежуточный результат, не прекращая goal.
5. Если работа долгая, оставляй последний подтвержденный Docker-срез доступным. Пользователь должен иметь возможность открыть промежуточный результат по данным из progress.
6. Тикет получает `DONE` только после каждого его критерия приемки, всех указанных автотестов и успешного `docker compose up --build -d` из актуальных файлов.
7. После `DONE` заполни финальную запись тикета, переведи следующий тикет в `IN_PROGRESS` и продолжай его в том же goal без запроса на новый Goal Mode.
8. После Ticket 014 выполни финальный полный прогон. Только если 001–014 имеют `DONE`, контейнеры healthy и C1–C8 проходят, отметь общий goal complete.

## Восстановление после сжатия контекста или паузы

В начале каждого нового хода не полагайся на память о прошлом ходе. Сначала:

1. прочитай `tickets/progress.md` целиком;
2. найди `IN_PROGRESS` и последнюю запись его checkpoint;
3. прочитай соответствующий ticket-файл;
4. проверь `git status`, файлы, миграции, тесты и Docker-контейнеры;
5. сопоставь журнал с фактическим состоянием;
6. продолжи с записанного «Следующего шага».

Если журнал и код расходятся, код + тесты + Docker являются доказательством фактического состояния. Исправь progress перед продолжением. Уже завершенный checkpoint не повторяй, если его результат по-прежнему подтверждается. Сжатие контекста не является блокером, причиной остановки или поводом начать проект заново.

Перед каждой потенциально долгой операцией запиши в progress, что запускается и какой результат ожидается. После операции зафиксируй фактический результат. Благодаря этому следующий ход должен продолжаться без дополнительного вопроса пользователю.

## Зафиксированный scope

- Реализуй только требования ТЗ и 14 подготовленных тикетов.
- Внешних интеграций и передачи обращений во внешние сервисы нет.
- Роли: заявитель, оператор, эксперт, администратор.
- Типы заявителя: школьник, родитель, педагог; дополнительных возрастных сегментов нет.
- Пользовательские сценарии: только C1–C8 из ТЗ.
- Frontend: mobile-first PWA на React + TypeScript, Axios, TanStack Query, Zustand, `@material/web`.
- Backend: ASP.NET Core, PostgreSQL, EF Core, Redis, Kafka.
- Первый тикет собирает .NET и Node внутри Docker; наличие SDK на хосте не считается условием.
- PostgreSQL — источник истины; Redis — временное состояние; Kafka — безопасные доменные события/аналитические проекции.
- Каждый тикет заканчивается запуском всего актуального проекта в Docker и браузерным checkpoint.

## Закрытые продуктовые решения и корнер-кейсы

Считай перечисленное решенным; не возвращай эти пункты пользователю как вопросы.

1. **Заметки.** Оператор не видит внутренние заметки и чат эксперта. Для передачи, соисполнителя и пересмотра приоритета существуют структурированные workflow-запросы без содержимого заметок.
2. **Кризис без контакта.** Показать `8-800-2000-122` и `124`, простые действия безопасности, предложить добровольный контакт и поднять тикет в кризисную очередь. Продолжать помощь в анонимном чате. Не устанавливать личность по IP/User-Agent и ничего автоматически не передавать наружу. Честно объяснить: без контакта и местонахождения сервис не способен направить физическую помощь.
3. **Кризисный приоритет.** Система ставит crisis flag и поднимает тикет; `Urgent` назначает только оператор. Кризисный тикет не закрывается обычным auto-close без ручной проверки.
4. **Трек-номер.** `ОТК-XXXX-XXXX`, CSPRNG, алфавит без спорных символов, хеш в БД, одинаковые ответы для неверного/несуществующего номера, rate-limit через краткоживущий Redis digest. Секрет не попадает в URL или логи.
5. **Потеря номера.** На том же устройстве помогает capability session/сохраненная страница. На новом устройстве номер не восстанавливается; пользователь создает новое обращение. Поиск по имени, телефону или тексту отсутствует.
6. **Повтор отправки.** Двойной тап и retry после сетевого сбоя идемпотентны и возвращают одно обращение/сообщение.
7. **Необязательные ответы.** Пропуск всех уточняющих вопросов не блокирует отправку. «Не знаю, как это назвать» всегда ведет к свободному тексту.
8. **Вложения.** До пяти файлов, до 10 МБ каждый; PNG/JPEG/PDF. MIME проверяется по содержимому, изображения перекодируются без EXIF/GPS, публичных URL нет. Ошибка одного файла не уничтожает текст формы.
9. **Нет эксперта.** Тикет остается в очереди оператора и подсвечивается администратору.
10. **Все перегружены.** Система предупреждает и оставляет тикет в очереди; ручное превышение лимита требует причины.
11. **Гонки.** Назначение, смена статуса, завершение/возврат и публикация рекомендаций используют optimistic concurrency и idempotency. Одновременный ввод экспертов защищен lease/presence с TTL.
12. **Передача.** После передачи старый ответственный теряет write-доступ, если не сохранен соисполнителем. У обращения всегда один ответственный; итог публикует он.
13. **Уточнение.** Ответ заявителя из «Нужно уточнение» автоматически возвращает «В работе» и уведомляет участников.
14. **Возврат.** «Это не помогло» всегда идет оператору. Максимум два возврата; затем оператор принимает обязательное итоговое решение с объяснением.
15. **Закрытие.** Закрытый рабочий цикл не переписывается. По новому решению Ticket 015 продолжение той же ситуации сохраняет общий трек и историю, а отдельная ситуация создает самостоятельное обращение.
16. **Жалоба.** Оператор видит текст жалобы и безопасные метаданные, эксперт жалобу не видит; чат и заметки оператору не раскрываются.
17. **Администратор.** Видит конфигурацию, метаданные, аудит и аналитику, но не тексты, чат, заметки, вложения и кризисный контакт.
18. **Аналитика.** Kafka events и CSV/XLSX строятся по whitelist метаданных. Тексты, свободные ответы, чат, заметки, файлы, контакты, трек-номера и технические идентификаторы заявителя запрещены.
19. **PWA/push.** Service worker кэширует только shell. Push нейтральный и не содержит текста, категории, приоритета или трек-номера. Отказ от push ничего не блокирует.
20. **Тон.** Со школьником — «ты», с родителем/педагогом — «вы»; сообщения поддерживающие, без обвиняющих красных ошибок и предупреждений о ложных сообщениях.

## Инженерные правила

- Сохраняй существующие пользовательские изменения; сначала проверяй `git status`.
- Используй `apply_patch` для ручного редактирования файлов.
- Миграции EF Core только последовательные; seed детерминированный.
- Host .NET/Node не используй как обязательную часть сборки или проверки.
- Все существенные проверки должны быть воспроизводимы в контейнерах.
- Текущий Docker-стенд должен оставаться рабочим после каждого checkpoint.
- Не маскируй проблемы удалением volume. Для чистой проверки используй явно документированный изолированный compose project/seed workflow.
- Не коммить и не отправляй изменения в remote без отдельной просьбы пользователя.
- Не добавляй функциональность сверх тикетов. Допустимы только внутренние технические изменения, необходимые для выполнения критериев.
- Если обнаружен дефект прошлого `DONE`-тикета, верни его в `IN_PROGRESS`, исправь, перепроверь зависимые срезы и только затем продолжай.
- Не останавливай goal ради обычной технической сложности. Исследуй код, логи, health-checks и альтернативы.

## Блокеры и общение

Сообщай короткий прогресс во время работы и всегда давай пользователю актуальный URL последнего рабочего среза. Не проси подтверждения между тикетами.

Если возник внешний блокер, который невозможно устранить кодом или локальной настройкой:

1. запиши точное условие, доказательства и попытки в progress;
2. сохрани последний рабочий Docker-срез;
3. продолжи независимую работу, если она есть;
4. пометь общий goal blocked только после трех последовательных goal-ходов с тем же блокером и отсутствием безопасного пути дальше.

## Финальное условие

Не объявляй проект готовым по количеству написанного кода. Готовность доказана только когда:

- все 14 строк в `progress.md` имеют `DONE`;
- `docker compose up --build -d` поднимает healthy-стенд из актуального состояния;
- C1–C8 пройдены;
- отрицательные проверки матрицы доступа пройдены;
- выгрузки не содержат текстов и контактов;
- README и DEMO позволяют воспроизвести запуск и сценарии;
- Ticket 014 содержит финальную запись и известные ограничения.

Только после этого отметь единый Goal Mode complete и сообщи пользователю итоговые URL, тестовые учетные записи, команды запуска, результаты C1–C8 и известные ограничения.
