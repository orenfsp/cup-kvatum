# Ticket 015 — Единый UX, навигация и непрерывная история обращения

Статус: `IN_PROGRESS`. Отдельный UX-этап после завершенного MVP 001–014 выполняется одним Goal Mode по checkpoints 1–6.

## Краткий checkpoint для заказчика

**Технологический стек:** mobile-first PWA на React и TypeScript с Material Web, Axios, TanStack Query и Zustand; backend на ASP.NET Core и EF Core; PostgreSQL для основных данных, Redis для временных состояний и ограничений, Kafka для обезличенных событий и аналитики; локальный запуск и демонстрация через Docker Compose.

**Идея:** анонимная платформа связывает человека, столкнувшегося с травлей, конфликтом или давлением, с оператором и профильным специалистом. Пользователь обращается без регистрации, получает трек-номер, сохраняет общую историю диалога и может продолжить ту же ситуацию без потери предыдущих ответов. Оператор маршрутизирует обращение, эксперт ведет диалог и готовит рекомендации, администратор управляет правилами и видит только обезличенные данные.

**План реализации:** сначала выстроить единую навигацию и общие UX-компоненты, затем переработать историю и кабинет заявителя, после этого — рабочие интерфейсы оператора, эксперта и медиатора, далее административную панель, и завершить этап проверкой текстов, адаптивности, доступности, безопасности и сквозных сценариев в Docker.

## Зачем нужен этап

Функции MVP работают, но интерфейс построен вокруг технических сущностей и отдельных API-действий, а не вокруг задач людей. В результате:

- кнопка «Написать снова» на экране обращения без объяснения переводит на новую форму;
- новый цикл помощи выглядит как несвязанное обращение, а прежняя история исчезает из текущего контекста;
- экран заявителя последовательно выводит статус, техническую хронологию, чат, рекомендации, исходы, жалобу, вложения и настройки устройства одной длинной страницей;
- служебный раздел переключается через локальный `activeSection`, поэтому адрес страницы не отражает раздел, Back/Forward не работают как навигация, прямые ссылки неполны;
- оператору одновременно показываются чтение, классификация, назначение, ответ и отклонение без устойчивой последовательности действий;
- эксперт получает команду, исходное обращение, диалог, заметки, рекомендацию и передачу в одной вертикальной карточке;
- эксперт по медиации не получает понятного контекста специализации, хотя должен использовать тот же предсказуемый рабочий интерфейс;
- административная конфигурация смешивает категории, группы и правила с постоянно открытыми формами;
- визуальный фундамент уже спокойный, но композиционные и навигационные паттерны еще не образуют единую продуктовую систему.

Цель этапа — сделать систему понятной без предварительного обучения: в каждый момент человек видит, где он находится, что произошло, что требуется сейчас и куда перейти дальше.

## Главная продуктовая концепция

### Обращение — это непрерывная история помощи

Для заявителя существует не набор технических тикетов, а одно «обращение» с устойчивым трек-номером и общей хронологией.

Внутри обращения может быть несколько рабочих циклов:

1. первоначальная подача;
2. разбор и работа специалиста;
3. рекомендация;
4. возврат или завершение;
5. при необходимости — продолжение той же ситуации.

Рабочий цикл после закрытия не переписывается и не открывается заново. Действие «Продолжить это обращение» создает новый цикл внутри той же истории. Заявитель остается под тем же трек-номером и видит предыдущие сообщения, ответы и решения.

Отдельное действие «Создать другое обращение» предназначено для новой, не связанной ситуации и выдает другой трек-номер. Эти два действия нельзя называть одинаково или располагать как равнозначные без пояснения.

### Правила продолжения

| Состояние | Главное действие заявителя | Результат |
|---|---|---|
| Специалист задал вопрос | «Ответить специалисту» | Сообщение добавляется в текущий диалог |
| Специалист еще работает | «Добавить сообщение» | Сообщение добавляется в текущий цикл |
| Есть рекомендация | «Нужна дополнительная помощь» | Текущий цикл возвращается оператору с причиной |
| Помощь подтверждена, цикл закрыт | «Продолжить это обращение» | Создается новый неизменяемо связанный цикл с той же историей и тем же треком |
| Ситуация другая | «Создать другое обращение» | Создается независимое обращение с новым треком |
| Обращение отклонено как спам/вне scope | Только ясное объяснение и «Создать другое обращение» | Старый цикл не маскируется под продолжение |

Фраза «Написать снова» больше не используется: она не объясняет, будет ли сохранена история.

### Видимость общей истории

- Заявитель видит весь собственный публичный диалог, все опубликованные рекомендации, свои исходы и последовательность циклов.
- Ответственный эксперт видит публичную историю, необходимую для помощи в текущем цикле, и первоначальные данные доступного ему обращения.
- Соисполнитель видит тот же рабочий контекст только пока является участником.
- Внутренние заметки не переносятся в публичную историю и не открываются новому специалисту автоматически, если он не является разрешенным участником соответствующего цикла.
- Оператор видит первоначальные сведения текущего цикла, безопасные итоги и структурированные причины возврата, но не читает экспертный чат и внутренние заметки.
- Администратор видит только служебные метаданные. Связь циклов не дает ему доступа к текстам, файлам, чату, рекомендациям или контакту.

## Информационная архитектура

### Публичный контур

Глобальная навигация:

| Название | Задача | Маршрут |
|---|---|---|
| «Обратиться» | Начать отдельное обращение | `/appeal/new` |
| «Моё обращение» | Ввести трек или открыть сохраненный доступ | `/appeal` |

Ссылка «Вход для сотрудников» переносится в спокойную служебную зону header/footer и не конкурирует с задачами заявителя. Старый `/appeal/status` остается совместимым redirect на `/appeal`.

Внутренние разделы открытого обращения:

| Раздел | Содержимое | Маршрут без секрета |
|---|---|---|
| «Диалог» | Публичная переписка и единственный composer | `/appeal/dialog` |
| «Ответ» | Последняя рекомендация, предыдущие версии и исход | `/appeal/answer` |
| «История» | Первоначальный рассказ, вложения, циклы и статусы | `/appeal/history` |
| «Доступ» | Трек, устройство и уведомления | `/appeal/access` |

Трек-номер, внутренний ID и capability никогда не помещаются в URL. Раздел маршрута не является секретом.

### Кабинет оператора

| Раздел | Маршрут | Главная задача |
|---|---|---|
| Очередь | `/staff/operator/queue` | Разобрать новое обращение и назначить специалиста |

Деталь обращения имеет собственный route: `/staff/operator/{section}/{appealId}`. Staff ID допустим в URL, поскольку маршрут защищен ролью и object-level access.

### Кабинет эксперта

| Раздел | Маршрут | Главная задача |
|---|---|---|
| Новые назначения | `/staff/expert/inbox` | Принять назначенное обращение |
| В работе | `/staff/expert/active` | Вести диалог и готовить помощь |
| Ждут заявителя | `/staff/expert/waiting` | Контролировать ожидаемые ответы |
| Завершенные | `/staff/expert/completed` | Смотреть доступную историю без случайного редактирования |
| Аналитика | `/staff/analytics` | Смотреть собственную разрешенную нагрузку |

Рабочая карточка: `/staff/expert/cases/{appealId}/{workspace}`.

Допустимые `workspace`: `overview`, `dialog`, `notes`, `answer`, `team`.

### Эксперт по медиации

Эксперт по медиации использует тот же интерфейс и те же маршруты, что остальные эксперты. Отдельная параллельная дизайн-система запрещена.

Различается только контекст:

- в header карточки явно указана группа или специализация «Медиация»;
- очередь по умолчанию может быть отфильтрована по доступным специалисту группам;
- терминология действий, диалог, заметки, рекомендация, команда и ограничения доступа остаются одинаковыми;
- соисполнитель и ответственный различаются обычной подписью роли, а не цветом или отдельным экраном.

| Раздел | Маршрут | Главная задача |

Конфигурационная цепочка «Категории → Группы → Правила» остается видимой как локальная навигация, но каждая сущность получает отдельную страницу.

## Общие правила навигации

1. Раздел, выбранная карточка и безопасные фильтры отражаются в URL.
2. Browser Back/Forward возвращает к предыдущему разделу и карточке, а не выбрасывает на старт кабинета.
3. После возврата из detail список сохраняет фильтры, сортировку и позицию прокрутки.
4. Переключение раздела не завершает staff-сессию и не очищает безопасный TanStack Query cache.
5. Несохраненный текст не теряется молча: переход требует явного подтверждения «Выйти без сохранения».
6. Текст обращения, заметка, сообщение, рекомендация, контакт и трек не хранятся в query string, hash, `localStorage` или `sessionStorage`.
7. После навигации focus переходит на заголовок нового экрана или detail; сообщение об успехе получает `role="status"`.
8. Route guard проверяет роль. Чужой маршрут ведет в стартовый раздел своей роли с понятным объяснением, но не раскрывает существование чужого объекта.
9. Все разделы имеют один постоянный способ вернуться к списку. Логотип не используется как скрытая кнопка «назад».
10. Критическое действие нельзя прятать только в tooltip, hover, контекстное меню или жест.

Для реализации используется нормальный route layer, предпочтительно `react-router-dom`. Индекс массива `activeSection` не является навигацией и должен быть удален.

## Интерфейс заявителя

### Экран доступа

Если защищенного доступа на устройстве нет:

- один короткий заголовок «Открыть моё обращение»;
- поле с постоянной меткой «Трек-номер»;
- действие «Открыть обращение»;
- пояснение, где найти номер и что на новом устройстве восстановить его нельзя;
- вторичное действие «Создать обращение», если номера нет.

Если capability существует, приложение сразу открывает обращение. Форма другого трека вызывается отдельным действием «Открыть по другому номеру» и не остается одновременно с рабочим экраном.

### Header обращения

На каждом подразделе показываются:

- «Обращение» и безопасно представленный трек с действием копирования;
- человеческий текущий статус без pill-фона;
- одна строка «Что сейчас происходит»;
- одна строка «Что можно сделать»;
- дата последнего изменения;
- локальная навигация «Диалог / Ответ / История / Доступ».

Техническая история статусов не должна стоять раньше сообщения или рекомендации, ради которых человек вернулся.

### Диалог

Диалог — основной экран возвращающегося заявителя.

- Первоначальный рассказ показывается первым событием «Вы рассказали», а не исчезает в отдельной форме.
- Сообщения идут в хронологическом порядке с понятными подписями «Вы» и «Специалист».
- Служебные смены статуса не разрывают переписку; важные изменения показываются спокойной строкой между сообщениями.
- Новый непрочитанный ответ приводит к последнему непрочитанному месту, а не безусловно в конец страницы.
- Composer существует только здесь и подписан по действию: «Ответ специалисту» либо «Добавить сообщение».
- Если писать сейчас нельзя, на месте composer находится причина и следующий шаг, а не просто исчезнувшее поле.
- Кризисная помощь появляется рядом с новым сообщением при маркере риска, но не перекрывает историю.

### Ответ специалиста

- Сначала показывается последняя актуальная рекомендация.
- Предыдущие версии доступны ниже в «Предыдущие ответы», свернуты по умолчанию.
- «Это помогло» и «Нужна дополнительная помощь» равнозначны по размеру и визуальному весу.
- Возврат объясняется до выбора причины: «Оператор пересмотрит обращение и подберет следующий шаг».
- Жалоба отделена от оценки полезности и остается спокойным вторичным действием.

### История

История организована по рабочим циклам, а не как бесконечный список технических enum-статусов.

Каждый цикл показывает:

- номер цикла и период;
- что было отправлено заявителем;
- публичный результат;
- исход: помогло, потребовалось продолжение или сервис завершил цикл;
- вложения заявителя;
- раскрываемую подробную хронологию статусов.

Последний цикл раскрыт. Завершенные циклы свернуты, но доступны с клавиатуры и screen reader.

### Продолжение после закрытия

После закрытого цикла показывается отдельный блок:

> Если речь о той же ситуации, продолжите это обращение — предыдущая история останется здесь. Если случилось другое, создайте отдельное обращение с новым номером.

Действия:

- primary: «Продолжить это обращение»;
- secondary: «Создать другое обращение».

После выбора продолжения открывается короткий composer «Что изменилось или какая помощь нужна сейчас?». Повторно проходить всю исходную форму не требуется. После отправки пользователь остается в `/appeal/dialog`, видит новый цикл и прежнюю историю.

## Интерфейс оператора

### Основная модель работы

Оператор работает не с универсальной карточкой, а с пятью ясными очередями задач. Каждая строка отвечает на четыре вопроса:

1. что требуется сделать;
2. насколько срочно;
3. сколько человек ждет;
4. есть ли препятствие для назначения.

Текст обращения не используется как preview в списке. В строке допустимы только разрешенные признаки: тип заявителя, категория, статус, приоритет, время ожидания, наличие файла, кризисный флаг и необходимость решения.

### Очередь

Desktop использует устойчивый master-detail:

- слева список шириной 320–380 px;
- справа рабочая область;
- header и навигация кабинета остаются на месте;
- выбор строки меняет route;
- после действия автоматически выбирается следующая карточка согласно сортировке.

На mobile список и detail являются отдельными экранами. Назад возвращает к тому же месту списка.

Фильтры группируются по задаче: «Новые / Проверенные / Без специалиста», затем категория, приоритет и время. Фильтры сохраняются в безопасном URL.

### Разбор нового обращения

Карточка строится как последовательность, а не как набор конкурирующих форм:

1. «Понять ситуацию» — первоначальный рассказ, ответы и вложения.
2. «Определить маршрут» — категория, приоритет и прозрачная подсказка.
3. «Назначить помощь» — подходящая группа, специалисты, доступность и лимит.

На экране одновременно раскрыт текущий шаг. Завершенный шаг показывает короткое резюме и действие «Изменить».

Primary action всегда соответствует этапу: «Сохранить разбор» → «Назначить специалиста». Отклонение и самостоятельный ответ оператора находятся в меню вторичных решений с предварительным объяснением последствий, но не маскируются и доступны с клавиатуры.

### Срочная помощь

- очередь отсортирована по времени срабатывания маркера;
- header detail первым показывает «Срочность еще не подтверждена» или «Срочность подтверждена» обычным текстом;
- экстренные контакты и добровольный контакт разделены;
- раскрытие контакта требует отдельного действия и объясняет аудит до нажатия;
- primary sequence: «Подтвердить срочность» → «Назначить специалиста»;
- невозможность физической помощи без контакта сформулирована честно, без обещаний.

### Запросы экспертов

Detail показывает только:

- тип запроса;
- причину, специально отправленную экспертом оператору;
- текущего ответственного и допустимых кандидатов;
- влияние решения на роли участников.

Чат и внутренние заметки не появляются даже как свернутые блоки.

### Возвраты

Сначала показывается структурированная причина «что не помогло», затем предыдущие безопасные решения оператора и варианты:

- назначить повторно;
- после второго возврата — завершить с бережным объяснением.

UI явно показывает «возврат 1 из 2» или «нужно итоговое решение», но не использует цветную капсулу.

### Ошибки и гонки

При изменении карточки другим оператором detail не исчезает без объяснения. Показывается:

- что именно устарело;
- действие «Открыть актуальную версию»;
- сохраненный локально безопасный выбор, если его можно применить повторно;
- запрет повторной отправки уже завершенного действия.

## Интерфейс эксперта

### Рабочая область обращения

Вместо одной длинной страницы используется трехуровневая структура:

1. глобальная очередь эксперта;
2. header выбранного обращения;
3. локальный workspace: «Обзор / Диалог / Заметки / Ответ / Команда».

На desktop список остается слева, выбранный workspace — в центре. Короткий контекст «статус, роль, категория, следующий шаг» может оставаться справа или в устойчивом header. На mobile каждый уровень является отдельным экраном с явным Back.

### Header карточки

Всегда видны:

- человеческий статус;
- роль специалиста: ответственный или соисполнитель;
- специализация/группа, включая «Медиация»;
- тип заявителя и форма обращения на «ты/вы»;
- следующий ожидаемый шаг;
- дата последней активности.

Кнопка «Взять в работу» располагается в header как единственное primary action, пока обращение не принято.

### Обзор

Содержит только стабильный контекст:

- первоначальный рассказ;
- структурированные ответы;
- вложения;
- краткую публичную историю прошлых циклов, если это продолжение;
- текущих участников без формы управления.

### Диалог

- Только публичные сообщения и composer, видимый заявителю.
- Над composer постоянно написано «Заявитель увидит это сообщение».
- Имя специалиста в публичном контуре не показывается.
- Состояние «Ждем ответа заявителя» объясняет, почему composer недоступен и куда перейти дальше.
- Ответ заявителя помечается как новое рабочее событие и возвращает карточку в «В работе».

### Внутренние заметки

- Только заметки и composer заметки.
- Постоянная подпись: «Видят только разрешенные участники обращения. Не видят заявитель, оператор и администратор».
- Никакой кнопки публикации заявителю в этом workspace.
- При совместной работе lease показывается непосредственно рядом с полем, которое он блокирует.

### Ответ

- Предыдущие опубликованные версии отделены от нового черновика.
- Новый ответ сначала открывается как редактирование, затем как preview «Так увидит заявитель».
- Primary action в preview — «Опубликовать ответ»; secondary — «Вернуться к редактированию».
- Только ответственный специалист может публиковать итог.
- После публикации интерфейс показывает дальнейшее состояние заявителя, а не оставляет пустое поле.

### Команда

Содержит:

- текущего ответственного и соисполнителей;
- присутствие в карточке;
- отдельное создание запроса на передачу, соисполнителя или приоритет;
- историю запросов и участников.

Форма запроса не находится рядом с внутренней заметкой. Причина запроса явно подписана «Эту причину увидит оператор».

## Интерфейс администратора

### Обзор

Обзор не дублирует аналитику. Он показывает только задачи администрирования:

- неактивные или неполные правила;
- группы без доступных экспертов;
- обращения без движения;
- последние безопасные изменения.

Из каждого пункта есть route в соответствующий раздел. Ни одного текста обращения на обзоре нет.

### Категории, группы и правила

Для каждой сущности применяется одинаковый паттерн:

1. page header с описанием влияния;
2. список или таблица;
3. primary action «Добавить»;
4. создание/редактирование в detail-панели или отдельном route;
5. подтверждение деактивации с описанием последствий;
6. результат и ссылка обратно к измененной строке.

Пустая форма создания не занимает верх страницы постоянно. Редактирование конкретной строки не смешивается с созданием новой.

На страницах сохраняется контекст цепочки:

- категория показывает связанное правило;
- группа показывает состав, лимит и используемые правила;
- правило показывает категорию, группу и версию;
- переход по связи открывает соответствующий detail, а не просто меняет select внизу страницы.

### Сотрудники

- список отделен от создания сотрудника;
- статус доступа выражен текстом и доступным действием, без pill;
- блокировка требует подтверждения с объяснением отзыва сессии;
- роль и доступность эксперта редактируются в одном detail;
- временный пароль показывается только после создания один раз с действием копирования;
- фильтры роли и состояния отражаются в URL.

### Зависшие обращения

Сохраняется строгая privacy boundary. Detail содержит только разрешенные метаданные и одну задачу разблокирования. Поля, которые не меняются, не выглядят как editable.

Перед сохранением показывается резюме «было → станет» и обязательная причина. После сохранения доступна ссылка на созданное событие журнала.

### Журнал

- хронология и detail разведены;
- фильтры находятся в URL;
- detail показывает actor, время, объект, причину и безопасные значения до/после;
- нет универсального JSON dump;
- значения обращения, чат, заметки, файлы, контакт и трек никогда не появляются.

## Формы и копирайтинг

### Общие правила

1. Заголовок говорит о задаче, а не о типе компонента.
2. Перед формой объясняется результат действия.
3. Метка поля существует всегда; placeholder используется только как пример.
4. Необязательность пишется рядом с меткой, а не объясняется после ошибки.
5. Одна форма — одно primary action.
6. Ошибка отвечает: что не получилось, что сохранено и что сделать дальше.
7. После успеха интерфейс показывает изменившееся состояние и следующий шаг.
8. Нельзя использовать внутренние слова `ticket`, enum, payload, capability, lease или workflow request в пользовательском тексте.
9. Школьнику интерфейс пишет на «ты», родителю и педагогу — на «вы».
10. Сотрудникам текст короткий и рабочий, но не канцелярский.

### Обязательные замены

| Сейчас | Должно быть |
|---|---|
| «Статус» в публичной навигации | «Моё обращение» |
| «Показать статус» | «Открыть обращение» |
| «Написать снова» | Контекстное «Добавить сообщение», «Продолжить это обращение» или «Создать другое обращение» |
| «Помог ли ответ?» | «Нужна ли еще помощь?» с равноправными действиями |
| «Вернуть оператору» для заявителя | «Попросить пересмотреть помощь» |
| «Открыть другое обращение» | «Открыть по другому номеру» |
| «Карточка уже изменилась» | «Обращение обновил другой сотрудник. Откройте актуальную версию» |
| «Workflow-запрос» | «Запрос оператору» |

### Тон ошибок

Формула:

> Не удалось выполнить действие. Введенный текст сохранен на этом экране. Проверьте соединение и попробуйте еще раз.

Красный используется только для текста/границы реальной ошибки, не для обвинения, срочности или обычного пустого состояния.

## Единая дизайн-система

### Характер

Интерфейс спокойный, взрослый, дружелюбный и нейтральный. Он не должен выглядеть детским, медицинским, полицейским, банковским или как панель мониторинга инфраструктуры.

Базовые качества:

- ясность;
- спокойствие;
- уважение;
- ощущение контроля;
- приватность по умолчанию;
- предсказуемость переходов.

### Неизменяемые визуальные ограничения

- только Onest Variable с полноценной кириллицей;
- Material Web — базовый UI kit;
- никаких градиентов;
- никаких status pills/badges с цветной подложкой;
- никаких декоративных буллетов, точек, opacity-ореолов и задвоенных маркеров;
- никаких подложек под обычный поясняющий текст;
- никаких tooltip для обязательного смысла;
- никаких постоянных декоративных теней;
- никакого цвета как единственного признака состояния;
- никакого бесконечного полотна из одинаковых карточек;
- никакой skeleton-анимации с полупрозрачными дублями; загрузка — текст и linear progress.

### Токены

Существующие `src/frontend/src/styles/tokens.css` остаются базой. Локальные hex, случайные радиусы и spacing вне токенов запрещены.

Обязательные семейства токенов:

- цвет: ink, secondary ink, primary, page, surface, line, focus, error, warning;
- spacing: 4, 8, 12, 16, 20, 24, 32, 40, 48, 64;
- radius: field 12, control 14, panel 20;
- typography: page title, section title, item title, body, helper, label;
- layout: public form, public reading, staff list, staff detail, staff wide;
- motion: fast 120 ms, normal 180 ms, без motion при `prefers-reduced-motion`.

Новый токен добавляется только если он нужен минимум двум компонентам и имеет семантическое имя.

### Поверхности и иерархия

- Card используется для формы, dialog, защищенного detail или самостоятельного actionable объекта.
- Обычные разделы отделяются whitespace и линией.
- Status — заголовок/текст плюс при необходимости доступная иконка, но не capsule.
- Primary action на видимой области один.
- Вторичные действия — outlined или text button.
- Опасные административные действия не становятся ярче основного рабочего пути; их риск объясняется confirmation dialog.

### Material-компоненты

Предпочтительно использовать:

- `md-filled-button`, `md-outlined-button`, `md-text-button`;
- `md-tabs` для локального workspace, если labels помещаются и остаются доступны;
- `md-dialog` для подтверждения необратимого действия и preview публикации;
- `md-linear-progress` для загрузки/отправки;
- `md-checkbox`, `md-radio`, `md-switch` только по их семантике;
- Material text fields/selects после проверки доступности кириллических labels и responsive.

Если у Material Web нет подходящего data-table или master-detail, используется семантический native HTML с общими токенами, а не имитация случайными `div`.

## Responsive-правила

### Public

- Минимум 320 CSS px без горизонтального scroll.
- Одна колонка до 720 px.
- Максимальная ширина чтения 720–760 px.
- Composer и primary action доступны без точного попадания, минимальная интерактивная высота 44 px.
- Локальная навигация обращения не обрезает labels; при нехватке места используется двухстрочная grid-навигация, а не скрытый горизонтальный scroll.

### Staff

- От 1200 px: sidebar + list + detail/context.
- 768–1199 px: sidebar/rail + один основной workspace; список может сворачиваться.
- До 767 px: список и detail становятся отдельными routes; никакого уменьшенного трехколоночного desktop.
- Role navigation на mobile открывается явной кнопкой «Разделы» в top app bar и полноценной modal side sheet. Это не icon-only hamburger: у действия есть видимая подпись.
- Нижняя навигация допустима только для 3–5 действительно постоянных разделов роли; «Еще» не скрывает срочную очередь оператора.

## Accessibility и безопасность взаимодействия

- WCAG AA: минимум 4.5:1 для обычного текста и 3:1 для крупного текста/границ meaningful controls.
- Полная keyboard navigation без ловушек.
- У каждого icon-only действия есть доступное имя, но предпочтительны текстовые actions.
- Focus-ring видим на всех native и Material controls.
- Открытие detail переводит focus на его заголовок; закрытие dialog возвращает focus инициатору.
- Ошибки связаны с полями через `aria-describedby`; первое ошибочное поле получает focus после submit.
- Dynamic status использует подходящий `aria-live`, но не перечитывает всю страницу.
- Таблицы имеют caption/headers; списки задач — доступное название.
- Touch target минимум 44×44 px.
- `prefers-reduced-motion`, zoom 200% и narrow viewport входят в приемку.
- Автосохранение не отправляет чувствительный черновик в browser storage, analytics или логи.

## Необходимые изменения модели и API

UX непрерывной истории нельзя корректно сделать только CSS-перестановкой.

Предлагаемая минимальная модель:

### `AppealThread`

- `Id`;
- stable track hash/recovery ciphertext;
- `CreatedAt`, `LastActivityAt`;
- `CurrentCycleId`;
- device grants и push subscriptions относятся к thread;
- один thread соответствует одному трек-номеру.

### `AppealCycle`

Текущая сущность `Appeal` становится рабочим циклом либо получает `ThreadId` и `Sequence`.

- закрытый cycle immutable в смысле workflow;
- новый cycle создается только командой продолжения;
- `Sequence` монотонный;
- idempotent `clientContinuationId` исключает двойное создание;
- current cycle один;
- старые статусы, рекомендации и публичные сообщения остаются привязаны к своему cycle.

### Миграция

- каждое существующее обращение получает отдельный thread;
- существующий track переносится на thread без изменения пользовательского номера;
- текущий appeal получает `Sequence = 1`;
- device capability продолжает открывать тот же thread;
- миграция обратимо проверяется на копии demo data, volumes не удаляются как способ исправления.

### Публичные endpoints

- `POST /api/public/appeals/open` — открыть thread по track и вернуть workspace payload;
- `GET /api/public/device-session` — вернуть доступный thread;
- `POST /api/public/appeals/continue` — создать следующий cycle с тем же track, только из допустимого terminal state;
- status payload разделяется на `summary`, `currentCycle`, `publicActivity`, `recommendations`, `cycles`, `permissions`;
- все команды имеют idempotency и optimistic concurrency.

Фактические route names можно сохранить совместимыми, но контракт должен отражать thread/cycle и не заставлять UI собирать смысл из разрозненных flags.

### Staff endpoints

- list endpoints возвращают `nextAction`, `lastActivityAt`, безопасные counts и специализацию;
- detail payload группируется по workspace, либо получает отдельные endpoints для тяжелых разделов;
- operator API не расширяется чатом/заметками;
- admin API не расширяется содержанием;
- текущий expert получает публичный контекст прошлых циклов только по object authorization.

### Аналитика

Перед реализацией фиксируются определения:

- «обращения» как threads;
- «циклы помощи» как cycles;
- нагрузка и SLA считаются по cycles;
- продолжение не должно незаметно удваивать основной показатель обращений;
- экспорт остается metadata-only и не включает stable track, public history или тексты продолжения.

## План выполнения

- старый track продолжает работать;

## Критерии приемки

Ticket 015 нельзя считать готовым, пока одновременно не выполнено следующее:

1. Один трек открывает всю историю одного обращения после продолжения.
2. Старый цикл не изменяется, новый виден как продолжение, а не несвязанный тикет.
3. На экране заявителя нет одной длинной страницы со всеми функциями; Диалог, Ответ, История и Доступ разделены.
4. «Написать снова» отсутствует; каждое действие однозначно сообщает результат.
5. Все основные разделы operator/expert/admin имеют URL и поддерживают Back/Forward/refresh.
6. Оператор выполняет triage и assignment как понятную последовательность.
7. Expert Dialog, Notes, Answer и Team не смешаны в одном полотне.
8. Медиатор работает в том же UX и видит свою специализацию/роль.
9. Категории, группы и правила администратора имеют отдельные list/detail routes.
10. Матрица доступа не ослаблена.
11. На 320 px нет horizontal scroll; на desktop нет чрезмерно пустого detail или бесконечного полотна.
12. Material Web и Onest используются последовательно.
13. Нет градиентов, status pills, декоративных bullets, opacity halos, текстовых подложек и essential tooltips.
14. Keyboard, focus, labels, screen-reader names и WCAG AA проверены.
15. Все checkpoints имеют рабочий Docker URL и доказательства в журнале.
